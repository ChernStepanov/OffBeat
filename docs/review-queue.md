# Очередь проверки изменений: рабочий MVP

Результат: открытая воспроизводимая очередь исследовательских проверок
Amazon с сопоставлением NISAR L-band HV, Sentinel-1 C-band VH, точечного
качества оптики и погодного контекста. Интерфейс находится над историей
изменения, в окне «Очередь проверок / NISAR + Sentinel-1».

## Что работает

- 575 образцов с историческим WorldCover 2021 = tree cover; все остаются
  одним development AOI. Ни один не объявлен независимо подтверждённым событием.
- Шесть пар SAR-дат. Используется только предыдущая/совпадающая S1-дата
  с разницей не более двух дней; проверяется SHA-256 порядка координат
  из исходного RTC receipt. Недостающая съёмка не заменяется нулём.
- Сравнение среднего остатка первых трёх и последних трёх дат. Фон —
  медиана того же класса на 300–1200 м, минимум 10 валидных соседей на дату.
  Это разреженные точки, не плотный растр и не площадь события.
- Кандидат: падение остатка хотя бы одного канала >=2.5 dB и минимум две
  последние даты ниже исторического среднего остатка. Знак положительный
  соответствует снижению backscatter. При таком правиле получено 58 точек,
  а не 58 независимых событий или вырубок.
- Фиксированный приоритет, фильтр кандидатов, пространственное разнесение
  проверок минимум на 300 м, переключение S1 / S1+NISAR / +evidence gaps.
- Карточка с исходным и остаточным сигналом, устойчивостью, согласованными
  датами, доступностью ясной SCL-пары и следующим действием. Переход в карту,
  карточку доказательств, ссылка на точную точку/дату и выгрузка свидетельств.
- JSON/GeoJSON очереди и отдельный JSON сравнения вариантов. GeoJSON —
  Point; контуры и площадь события не выдумываются.
- Экспорт исследовательских заметок с reviewer/source/observation. Просмотр
  рейтинга означает отсутствие blinding: `independent=false`,
  `blind_to_scores=false`, `split=development`, `label=unknown`.
  Такая заметка не может использоваться как независимый тест или обучение.

## Формула приоритета и границы

Для канала с полной поддержкой:

```
channel_score = max(0, residual_mean_drop_db / 2.5)
                + 0.25 * post_dates_below_history / post_date_count
fusion_score = max(L_score, C_score)
               + 0.25, если каналы находятся по разные стороны порога 2.5 dB
context_score = fusion_score
                + 0.25, если ясная оптическая пара в точке не установлена
```

Объединённый балл требует оба канала. Значения — эвристические приоритеты,
не проценты вероятности и не физический диагноз. Пороги одинаковы в dB
для простого development-сравнения, но не означают одинаковую чувствительность
двух сенсоров. Расхождение включает различия геометрии/времени/разрешения.

Точечное качество оптики есть только для ранее исследованных координат
из `amazon-spatial-external-audit-v2.json`. SCL 4/5/6 допускает ясное наблюдение;
3 (тень), облака, будущие даты исключены. Большинство координат не проверены;
ясность всего AOI не переносится на них. SCL 4→5 не является самостоятельной
истинной меткой потери леса. Система рекомендует следующую проверку, но не
производит автоматически независимый визуальный/полевой разбор.

Осадки за 7 предыдущих полных UTC-дней показываются как контекст. В эвристике
нет подавления кандидатов «из-за дождя» и причинной погодной коррекции.
В обучаемом варианте контекст включает разницу среднего rain_7d между
последними и первыми тремя SAR-датами плюс флаг недостающей ясной пары.

Весь срез ретроспективный: даты съёмок согласованы, но продукты могли быть
опубликованы позже. Погодный архив и SCL-разбор получены позднее периода SAR.
Историческая operational availability не доказана. Нет заявления о раннем
оповещении, чувствительности к биомассе, повреждениях зданий или экономии времени.

Фильтр кандидатов в UI — объединение кандидатов обоих каналов, одинаковое
для переключаемых вариантов. Это средство исследования, не автономная
S1-only система, работающая без доступа к NISAR. Количественное сравнение
в `comparison-v1.json` использует общий полный набор пригодных лесных точек,
затем для каждого метода отдельно разносит места проверки и берёт бюджет 10.
Результат сравнения — состав рейтинга; качество событий неизвестно.
Разнесение на 300 м снижает дублирование проверок, но не создаёт независимых событий.

## Собственная обучаемая модель

`pipeline/review_learning.py` реализует бинарную логистическую модель и
калибровку Platt по отдельным event-группам. Выбор простой модели позволяет
начать с проверяемого baseline и CPU без скачивания больших весов.

Три обучаемых варианта:

1. S1 residual drop, последнее residual change, устойчивость.
2. То же + соответствующие признаки NISAR.
3. То же + недостаток ясной оптики и изменение погодного контекста.

Группы целиком относятся к `train`, `calibration` или `test`. Члены каждой
группы агрегируются в одно событие, поэтому множество соседних точек не
увеличивает число test events. Mean/std вычисляются только на train;
Platt — только на calibration; test не настраивает модель. Варианты требуют
одного полного набора признаков; пропуски не заполняются нулями. Пересечение
разных split ближе 2400 м запрещено. Это необходимый, но недостаточный буфер:
геометрия реального события/атмосферной зависимости может требовать большего.

Метки должны быть confirmed/refuted/unknown. Unknown исключаются из обучения.
Для известных меток необходимы reviewer, заявление о независимости и blinding,
соответствие spatial support, независимо ограниченный интервал события либо
стабильного контроля, минимум 2 гарантированные SAR-даты до и 2 после.
В этой версии формулы признаков фиксированы на шести датах: поэтому дополнительно требуются три гарантированные даты до всего интервала и три после, без загрязнения исторической половины событием.
Сохранённые исходники независимых свидетельств проверяются по SHA-256.
Исходный predictor receipt не может одновременно служить independent label receipt.

Код проверяет структуру и согласованность; флаг `blind_to_scores=true`
сам по себе не доказывает реальную независимость. Нужна отдельная процедура
слепого разбора человеком, а не переписывание флагов в заметке из интерфейса.
Разделение AOI на train/test после просмотра рейтинга недопустимо.

**По текущим реальным данным модель не обучена.** В
`independent-labels-v1.json` 0 записей. Статус
`not_trained_missing_independent_events`, accuracy и экономия проверок — null.
Существующие 575 development-пикселей нельзя просто переименовать в train/test.
Нужны новые независимо проверенные event-группы и новая версия протокола/очереди.
Синтетические данные используются только в тестах, не включены в production artifacts.

## Формат независимой разметки

`queue_sha256` связывает файл с точными байтами подготовленного датасета
очереди. Пример структуры ниже — **не настоящая метка**; заполнители нельзя
использовать для отчёта о научном качестве:

```json
{
  "schema_version": 1,
  "queue_sha256": "<sha256 подготовленного датасета с новыми event-группами>",
  "records": [{
    "sample_id": "<существующая точка в этом датасете>",
    "event_group": "<группа, заранее назначенная протоколом>",
    "split": "train",
    "label": "confirmed",
    "independent": true,
    "blind_to_scores": true,
    "reviewer": "<кто выполнил независимую проверку>",
    "spatial_support_match": true,
    "interval": ["<последняя уверенная дата до>", "<первая уверенная дата после>"],
    "sources": [{
      "path": "<локальный файл независимого свидетельства>",
      "url": "<исходный URL>",
      "sha256": "<хеш сохранённого файла>",
      "observed_date": "<дата съёмки YYYY-MM-DD>"
    }]
  }]
}
```

Новый исходный queue dataset должен хранить у каждой точки `dates`,
`sample_id`, `event_group`, `split`, `lat`, `lon`, вычисленные `l_band`,
`c_band`, `optical.status`, `rain_pre_post_difference_mm` по тем же формулам.
Группы/split назначаются **до** выбора лучшего рейтинга, а не импортируются
из review labels. Изменение membership/splits требует версии протокола
и воспроизводимых исходных receipts. Текущий генератор обслуживает только
зафиксированный Amazon development AOI; он не скачивает новые участки.

Программный минимум — по 2 положительных и 2 отрицательных независимых
события в каждом из трёх split. Это лишь минимум для выполнения кода,
не достаточное количество для доказательства глобальной точности.
Сначала нужно собрать независимую выборку в нескольких регионах и согласовать
с аналитиками стоимость пропуска события/ручной проверки. Автоматического
подтверждения причин или контактов с внешними аналитиками здесь нет.

## Сравнение качества после появления разметки

При фиксированном бюджете выводятся event precision/recall, top event IDs,
Brier score, а при заранее заданной target recall — число проверок до её
достижения и относительное снижение против S1-only. Если событий меньше K,
precision@K остаётся null. По текущему пустому независимому набору все
метрики качества неизвестны, а не 0% ошибок.

Целевой эффект: 25% меньше проверок при сопоставимой полноте. В CLI
зафиксирован исходный target recall 0.8; менять его после просмотра test
нельзя. Параметры/порог/бюджет необходимо согласовать и закрепить в новом
протоколе до эксперимента с реальными событиями. Отрицательное снижение
означает рост количества проверок. При маленьком числе событий оценки
неустойчивы; доверительные интервалы и внешнюю валидацию нужно добавить
после сбора достаточного независимого набора.

## Команды и артефакты

```sh
# Рассчитать development-очередь из сохранённых реальных источников
python3 -m pipeline.review_queue
# Проверить актуальность без изменения артефактов
python3 -m pipeline.review_queue --check
# Зафиксировать честный статус обучения на текущей пустой разметке
python3 -m pipeline.review_learning
# Позднее: независимая многособытийная выборка
python3 -m pipeline.review_learning --queue path/to/new-queue.json \
  --labels path/to/independent-labels.json --budget 10 --target-recall 0.8 \
  --output path/to/model-and-evaluation.json
# Научные ограничения и алгоритмические регрессии
python3 -m unittest pipeline.tests.test_review_queue_unittest -v
node scripts/test_navigation.mjs
node scripts/test_evidence.mjs
node scripts/version_assets.mjs --check
```

Не перезаписывать файл независимой разметки пустым при обновлении очереди.
При изменении её исходных байтов обучение остановится из-за несовпадения
`queue_sha256`: нужна проверенная новая версия датасета и разметки.

Артефакты:

- `data/review-queue/protocol-v1.json`: фиксированные development-параметры.
- `amazon-v1.json`, `amazon-v1.geojson`: очередь, признаки, provenance и SHA-256.
- `comparison-v1.json`: сравнение рейтингов на общем наборе, неизвестные event metrics.
- `independent-labels-v1.json`: честный пустой независимый набор.
- `learning-status-v1.json`: статус модели, SHA-256 кода/входов, параметры обучения.

Готовые TerraMind/Prithvi пока не запускались. Интерфейс не подменяет их
сгенерированными данными. Следующий этап после независимой разметки и baseline —
реальные плотные S1/S2-патчи, frozen encoder и обучение небольшой головы;
прямой подстановки NISAR HH/HV в VV/VH-вход нет. Исходная стратегия и условия
выбора внешнего encoder: `docs/ml-strategy-2026-11-15.md`.
